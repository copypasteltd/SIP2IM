# Android gateway foundation

This is an incomplete foundation, not a usable gateway. **Status update 2026-11-21:** a debug APK was built and JVM tests were run; older “unbuilt” statements below refer to earlier work and do not mean the current debug build is absent. No physical-device acceptance has occurred. See [handover](../docs/18-开发部署与交接现状-2026-11-21.md). It contains the Android/JVM module layout, binary media framing, event IDs, persistent event outbox, private credential storage, OS tier classification and emergency-number helper. There is an unverified HTTP binding form and foreground WebSocket service skeleton, transport-independent connection sequencing, command field validation, a local pause screen, and same-broadcast SMS part assembly. SMS commands now have durable reservation, SIM and permission validation, at-most-once submission and transactional callback results in the outbox; this integration is unbuilt and has not been exercised on Android. call.dial and call.answer receive fail-closed responses. `hello.ok` and `config.update` validate and persist heartbeat interval (1–86400 seconds) and locale (en, zh-CN or zh-HK); configuration commands and their acknowledgments are committed together. The service reschedules its heartbeat after accepted updates; the saved locale takes effect when the activity is next created. This behavior is unbuilt and unverified. Call reject and hangup receive fail-closed unsupported responses. Heartbeat defaults to 30 seconds and uses the persisted configured interval. Unobservable network or Shizuku state is sent as `unknown`; Shizuku observation also reports a confirmed missing package or an active binder; API levels below 24 report unsupported because the pinned Shizuku API artifact declares minSdk 24. Upgrade core to a version accepting these values before deploying this APK: older receivers may silently reject the heartbeat without disconnecting, so liveness can still expire. This behavior is unbuilt and unverified. Battery and charging use system observations and signal strength remains unknown. The debug APK now builds with Shizuku 13.1.5: the library minSdk overrides are paired with a provider disabled by default and enabled by an API 24 resource, and Shizuku API calls are isolated behind an API 24 guard. This packaging has not been verified on an Android device, including API 19 startup or Shizuku binder delivery. After hello succeeds, the connected service checks observed SIM inventory and permissions on the heartbeat schedule, sends snapshots on changes, retries unacknowledged snapshots on a later check, and refreshes acknowledged snapshots periodically. SIM inventory is nonauthoritative. If SIM inventory cannot be observed, the snapshot is suppressed, so the server may retain stale status until a later successful observation. Delivery callbacks are ignored: `RESULT_OK` alone does not establish carrier delivery, and status-report PDU decoding and device validation remain outstanding; no `delivered` result is emitted by this callback path. START_STICKY and a boot receiver request service restoration on a best-effort basis; Android restrictions, force-stop and device behavior can prevent it, and opening the bound app retries startup. A callback that cannot be written after bounded retries may be lost; a claimed submission remains unknown and is never replayed. SMS receive assembly remains limited to a single broadcast. Call control, audio bridging, Shizuku authorization and privileged services are not implemented. The tier describes OS version only and must not be reported as a verified capability.

Build requires JDK 17, Android SDK platform 35, and Gradle 8.x (AGP 8.7.3 requires Gradle 8.9). The Gradle wrapper is not included because no verified wrapper distribution was available in this environment. Once a trusted Gradle 8.9 is installed, generate and verify its wrapper, then run `gradlew :protocol:test :app:testDebugUnitTest :app:lintDebug :app:assembleDebug`. Shared protocol fixture conformance remains outstanding. JDK 17 is available in the project toolchain; SDK license and installation remain pending. Dependencies need project-level notices registration.

## Binding and SMS execution fence

The app uses the existing v1 binding API and the existing device WebSocket. On a fresh installation, binding validates the address and code, commits a pending local identity to `gateway.db`, then sends the binding request. A validated response promotes the exact pending identity and stores the device ID, origin and credential in the same record. An unresolved request stays pending across restart. The existing v1 HTTP transport supplies no cryptographic server authentication.

The app commits an open-connection marker before it creates a socket. A normal transport loss releases the marker and reconnects with a fresh generation. The socket must receive a `hello.ok` whose string `deviceId` exactly matches the stored binding before the app applies hello configuration or authorizes work. Close codes 4003, 4005, 4010 and 4011, and a missing or mismatching hello identity, block the binding across restart. An open marker left by abrupt process death requires reconciliation because the app cannot determine whether it observed a terminal close before the exit. The close blocks new local submissions once observed. A submission admitted before the close can still reach Android. An unreachable device may receive no revocation signal.

An outgoing SMS task belongs to the binding and connection generation that reserved it. Queue selection and claim use both values. The app checks current authorization and local pause before claim and again before calling Android. Old queued tasks remain in storage for reconciliation. Late results from an already claimed task retain the task's binding. An exact duplicate within the same binding can still receive its original command acknowledgement under the existing protocol. Acknowledgement records queue acceptance and does not confirm submission. Local pause holds the current queue and continues heartbeats and inbound uploads.

Incoming SMS is persisted before it notifies an existing service. It also persists while the service is absent, paused or blocked. The receiver does not start the service. An incoming message captured under a verified binding can upload after a transport reconnect. Rows without proven ownership remain local. Duplicate broadcasts are currently stored as separate events.

## Upgrade and operator recovery

The additive Android SQLite v4 upgrade keeps outbox records, SMS commands, tasks and parts. A pre-v4 database or old credential preferences require reconciliation. The app does not adopt the old credential or assign old rows to a new binding. For a blocked installation, preserve the app data and investigate the recorded identity and old SMS outcomes with the administrator. Preserve the databases with their journals and handle the data as sensitive. Gateway storage contains a credential and message contents. A supported cutover needs an approved way to establish prior identity ownership, retire or reconcile the old server binding and decide which records can be associated. A fresh v1 hello would establish current acceptance but could not establish whether a previous terminal close was lost at restart. The app provides no binding reset or replay path. Clearing data, restoring a snapshot or running an older APK bypasses the supported recovery assumptions.

The focused JVM regression classes are `BindingFenceTest`, `CooperativeDrainTest` and `GatewayConnectionObservationTest` in the app. Run the local migration fixtures from the repository root with `python -B android/app/src/test/test_binding_fence_sqlite.py -v`. These fixtures use desktop SQLite and synthetic data.

No emulator or device was used. SMS, telephony, audio, Android lifecycle, permissions, and API 19 compatibility remain unverified; device voice operation requires the separately authorized G0 human listening test.
