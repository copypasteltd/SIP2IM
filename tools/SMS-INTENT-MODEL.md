# SMS durable intent: executable model

Run from the repository root: `python -m unittest discover -s tools -p test_sms_intent_model.py -v`. Only the Python standard library is required. This is a model, not production storage or browser integration.

Assumptions: each store method is a serializable atomic transaction with durable commit and all-or-nothing abort. Identity is (server, key), shared across owners; immutable fields are owner, server, key, SIM, recipient and body. Normal admission permits at most one pending or conflicted intent per server; legacy migration is exempt so divergent existing intents survive. Tombstones retain the complete immutable intent indefinitely and reserve its key; same-key different-payload variants are durably retained as conflicts and block admission on that server. A tombstone acknowledges only its exact immutable variant; conflicts remain unresolved. Cleanup verifies a committed pending record or matching tombstone or conflict and removes only the unchanged tab value. Session identity is represented by owner/server, without an authentication-generation token. Server strings are assumed to be canonical, stable identifiers: aliases for one server are not normalized and would form separate namespaces. Each legacy tab is assumed to have a single writer, with its comparison and deletion effectively atomic against changes; the model does not establish that property for real storage or old code. These are modeling choices, not established product policy.

Tests use sequential deterministic scheduling to enumerate both serialization orders; they do not run threads. Tests simulate a crash after migration commit and before cleanup, and model delayed migration against acknowledgement. They check rollback, conditional acknowledgement, changed legacy content, malformed data and conflicts. A callback records whether POST was attempted after admission; there is no network. The callback immediately follows commit and assumes the session remains valid across that boundary: session changes between admission and POST and callback revalidation are not modeled or verified.

The model assumes storage is durable and transaction isolation works; it does not test IndexedDB, real tabs, actual process crashes, storage eviction, broadcasts, old-tab fencing, account-generation changes, network responses, lookup/retry, or physical delivery. A tombstone is retained without garbage collection; production retention and fencing require separate design. It does not establish exactly-once delivery.
