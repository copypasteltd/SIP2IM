# Core foundation

This package contains configuration validation, the documented PostgreSQL schema and initial settings migrations, a migration runner, authentication primitives and repository, device freshness and eligibility rules, SMS state/rate rules, and call transition/lock primitives with repositories. An initial executable server and CLI are included.

The reducers are building blocks, not a complete coordinator: event ordering, timer scheduling, leg management, event emission, restart cleanup and transport integration remain to be implemented. In particular platform outbound events arriving before the command acknowledgement need durable buffering or equivalent ordering logic. Do not connect these primitives to actual calls or SMS without completing those paths. SMS repository insertion, state compare-and-set and restart marking do not yet constitute a queue dispatcher. Device binding, SIM synchronization, HTTP/WebSocket endpoints, admin creation, and migration startup wiring are also pending.

Run npm run check and npm run build in this directory after installing dependencies. PostgreSQL integration must use only the explicitly authorized test database; no server is started by these tests.

An initial HTTP/device WebSocket slice and migration/admin CLI are now present. Snapshot, inbound SMS and SMS result events have initial transactional processing and acknowledgements; other device business events remain incomplete; do not deploy or use with real devices until implemented. HTTP bodies and WebSocket frames are capped at 64 KiB. The mandated Zod 3 dependency has an unresolved production advisory GHSA-mrhx-c7xc-m3w5; input size limits reduce exposure but do not resolve it.
Outbound SMS parts is stored as 1 by the current schema default even though actual segmentation is unknown; sms.result supplies no authoritative part count. This value must not be interpreted as a measured count. Correcting it requires a nullable/unknown schema and DTO contract plus an authoritative device report.

When the same device reports conflicting failed and sent/delivered evidence for one task, Core conservatively marks the outcome unknown regardless of arrival order and does not retry. Unknown followed by a device failed result resolves to failed. Any device result conflicting with a recorded negative ACK or a pre-dispatch local failure becomes unknown with SMS_RESULT_CONFLICT; conflicting failed versus sent/delivered evidence also becomes unknown. Replaying the same evidence does not change this decision. Migration 0015 records negative acknowledgement and pre-dispatch local failure provenance atomically. Migration 0015 marks pre-existing failed tasks as legacy failures without assuming their origin; existing or subsequent same-device sent/delivered evidence makes them unknown. Historical origins cannot be reconstructed. CONFLICT can indicate an earlier reservation. The error code is reserved for Core and device events cannot supply it. Startup reconciliation replays stored results in the same transaction as dispatched-to-unknown recovery. SMS task updates are republished on duplicate result events when publication fails after commit; clients should also refresh state on reconnect because notifications are not a durable outbox. Inbound sms.new publication can still be lost after commit if read or publish fails; the stored message remains available via history and reconnect refresh, but reliable notification requires a durable outbox and consumer deduplication.

SMS v1 now accepts an additive unknown result. Upgrade all Core receivers before deploying the Android sender: older v1 receivers reject unknown and do not acknowledge it. Android commits the claim and unknown event together before modem submission, and retains the event until acknowledged. Unknown is never retried; later same-device callback evidence can resolve it to sent or failed. Existing older Android senders remain accepted. This is coordinated deployment, not capability negotiation; do not roll Core back while the new Android is active.

Call locks deliberately refuse takeover after four hours until the owner releases them. This fails closed when a call is still active, but differs from the documented four-hour expiry; recovery/reconciliation and a specification decision remain necessary.
SMS thread pagination is a live view ordered by latest message time. Threads that receive messages while pages are being read can move to an earlier page; clients should refresh the first page to capture changes. A simId query value of null selects messages whose SIM is unknown.

Presence notification compatibility: Core currently emits `device.updated` for heartbeat and offline-sweep changes, including online/offline transitions. It does not emit `device.online` or `device.offline` for these transitions, although those event types remain in the protocol and design documents. Consumers that only listen for transition events will miss presence changes and must also listen for `device.updated` and refetch device state; the bundled Web client already invalidates its device and dashboard queries. These notifications are best-effort invalidation hints, not an ordered or durable event stream. The embedded device snapshot may be stale or arrive out of order; refetch on each hint and after reconnect. A durable, versioned transition stream and associated consumer support are still needed if every transition must be observed. Administrative disable/revoke can race notification reads and does not itself promise a presence transition notification.
