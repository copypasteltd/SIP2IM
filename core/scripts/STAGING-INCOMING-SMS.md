# Isolated staging incoming SMS harness

**The operator must independently verify that the Core behind the configured port is isolated staging, including its database, workers, integrations and connected devices.** Literal loopback and opt-in do not prove isolation: a proxy or port forward may lead elsewhere. Never run against production or with real devices connected. The incoming event can trigger configured downstream integrations; disable or isolate them first.

Provide a dedicated staging administrator token and fresh staging binding code externally using a secure environment mechanism. Set CORE_STAGING_OPT_IN=yes, CORE_STAGING_ORIGIN to a literal http://127.0.0.1:PORT or http://[::1]:PORT, CORE_STAGING_ADMIN_TOKEN, and CORE_STAGING_BINDING_CODE. From core run `node scripts/staging-incoming-sms.mjs`. Never put secrets in arguments, logs, history or source; clear them afterwards. This script starts no service and is not part of ordinary tests.

A uniquely named fake WebSocket device binds and reports a synthetic SIM. A synthetic sender and body are sent in an incoming event, its ACK and a single matching row from the authenticated, device-filtered SMS history API are checked. The exact same envelope, including event ID and timestamp, is sent again and must ACK without creating another row. One differing body with the same ID and timestamp is sent once; current Core silently rejects it rather than returning a negative ACK. An independently identified snapshot ACK provides a FIFO processing barrier; the next frame must be that ACK, and the history must still contain exactly the original row. This checks no conflict ACK before the barrier, not an explicit rejection response. SIM attribution is deliberately null even when a slot/subId is reported: timestamps and observed SIM lifecycle do not establish which SIM received the SMS.

Writes and sends are not automatically retried except the explicitly required exact duplicate. A lost reply may still have changed state; inspect staging manually before retrying. The socket is terminated and only the known, newly bound synthetic device is soft-revoked once, with authenticated 404 verification. A failed bind may leave an unidentified device. Soft revocation does not remove device, event, SMS, or outbox records. Interruptions and cleanup failures require manual inspection. No real device, cellular network, or SMS is involved; server logs and downstream systems are outside this harness's control.
