# SMS dispatch uncertainty: unresolved gaps

The current dispatcher does not send during a flush when its queued-to-dispatched claim throws. A commit response can be lost after the claim commits, or the transaction can roll back; the exception alone does not distinguish these outcomes. The current claim path has no durable attempt identity. A later flush may encounter the task again if it remains queued; a dispatched task may instead remain stranded. A state-only dispatched-to-unknown update could alter a claim owned by another dispatcher, and a startup-wide recovery assumption does not establish ownership. FIFO and notification behavior across this failure are not guaranteed.

The send exception handler is separate from ACK persistence. A failed negative-ACK write is surfaced without a subsequent generic unknown transition. This does not make the ACK durable: if its transaction did not commit, a later device result can be processed without the negative-ACK conflict marker. A release failure can also hide a committed change and its notification. Retrying the same state CAS is at most best effort: it may find an advanced state and cannot establish that the marker was persisted.

A future solution needs a durable, uniquely identified dispatch attempt with fenced ownership, an idempotent durable ACK record independent of the current projection, and transactionally serialized result reconciliation and notification recovery. It must define how an unresolved attempt is surfaced and resolved across crashes and workers without blind resend, preserve per-SIM FIFO, and test commit-applied, rolled-back, release failure and concurrent-result cases. This is a design requirement, not implemented recovery. No real database or device validation was performed for this finding.
