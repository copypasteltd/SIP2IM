# 多设备安卓短信与电话云网关：总体需求与解决方案

> 当前版本：2026-11-20；需求已按用户决策更新。无 SIP/MIT 电话音频与 QQ/TG 桥接尚未证明可行，本文不是已运行系统或部署授权。

## 1. 项目目标和约束

一名管理员使用自建内网 Admin 管理至少 3 台旧安卓专机，架构支持 20 台以上；每台安装一个业务 APK，以 SIM 收发 SMS 和电话。支持浏览器实时电话、QQ/TG 来电转接和消息触发外呼。手机无需 Root，接受独立 Shizuku 及手机重启后的人工恢复，不增加蓝牙、声卡或其他外接配件。用户要求项目 MIT 开源、完全不使用 SIP 相关内容；服务原生运行，禁止调度 Docker、WSL 或其他虚拟化环境。

用户只保留一位管理员，不做复杂角色体系；设备认证和配对目标身份是系统必要身份，不是多用户 Admin。系统先在内网运行，关闭 CORS 校验，项目不配置 TLS，公网转发由用户自行处理。业务内容永久保存、不脱敏；不要求备份，故不承诺故障恢复能力。

## 2. 当前功能需求

| 编号 | 功能与验收目标 |
|---|---|
| DEV-01 | 短期一次性设备绑定；独立设备标识、可撤销；至少 3 台接入并设计/容量测试 20 台以上。 |
| DEV-02 | 后台分别显示设备心跳、SIM、电话控制、SMS、Shizuku、音频验证和 QQ/TG 状态；在线不等于可通话。 |
| DEV-03 | 管理员可录入设备/SIM 号码，区分人工、设备上报、已验证、未知；换卡须复核。 |
| SMS-01 | 同步上线后的新 SMS，后台按设备/SIM 查看；Unicode 和长短信纳入实测。 |
| SMS-02 | 后台发送 SMS，展示排队、已接收、已发送、失败、未知和实际收到的送达回执；未知不自动重试。 |
| CALL-01 | 浏览器通过指定设备/SIM 发起及接听电话，双方实时语音；先以桌面 Chrome/Edge 验收。 |
| IN-01 | SIM 来电先振铃，呼叫绑定 QQ/TG 目标；目标真实接听且媒体可用后再接听蜂窝；未接听则蜂窝不应答。 |
| IN-02 | 默认一个 SIM 一个主目标，一个目标可关联多台设备；初始振铃 20 秒可配置，不并行、不自动备用。 |
| OUT-01 | 配对用户向平台桥账号发送 {拨出号码}/{目标号码} 时按 SIM 号码唯一匹配；只发 {目标号码} 使用默认设备/SIM；有效消息立即拨号。 |
| OUT-02 | 先发起蜂窝外呼，再向消息发送者发起 QQ/TG 原生语音回拨；双方接听后桥接。被叫可能先接听并产生费用。 |
| PAIR-01 | Admin 登录各平台专用桥账号，生成一次性配对码；用户私聊发送后绑定即生效，不作二次确认，并同时授权来电和消息外呼。 |
| OPS-01 | 设备离线、SIM/短信/Shizuku/音频/平台失败分别告警；状态未知要如实显示。 |

配对码建议 5 分钟、5 次尝试、原子单次消费，已接受推荐，可配置；仅允许私聊，不接受转发消息。管理员可撤销配对。配对码泄漏会导致抢占，此风险不能靠昵称识别消除。真实平台 sender ID 与可拨号目标 ID 的映射须按平台实测。

## 3. 直接媒体架构（拟实现，非已验证）

```text
QQ/TG 用户 ⇄ 平台原生语音适配器 ⇄ 呼叫协调/媒体路由 ⇄ 安卓网关 ⇄ 蜂窝 SIM
                   ▲                       ⇅
            消息/配对适配器         浏览器 WebRTC
                                           ⇅
Admin ⇄ HTTP/WS ⇄ TypeScript API + PostgreSQL ⇄ Android 网关
```

电话状态、媒体帧和业务消息分离；云端管理后台负责设备、短信、呼叫、配对和告警。用户要求无 SIP，因此不部署 SIP 服务，也不复用包含 SIP 的电话上游。传输候选 WebRTC 或许可兼容的直接音频流，具体协议、平台接入和连接拓扑必须以许可证审查和 POC 为准。各腿独立终止，桥能接触音频，不声称端到端加密。

技术方案由助手选择：Kotlin Android、TypeScript/NestJS 后端、PostgreSQL、React/TypeScript Admin；这些为当前选型，媒体库和 QQ/TG 适配器仍未决。浏览器麦克风通常需要 HTTPS 或 localhost 安全上下文，普通内网 HTTP 可能不可用；项目不配置 TLS，依赖用户后续代理或可验证的安全上下文，不能绕开浏览器约束。WebRTC 强制的媒体安全机制与部署 TLS 证书并非同一概念。

## 4. 功能流程

### 短信

设备接收新短信 → 事件有设备和 SIM 来源、唯一 ID、时间及正文 → 持久化并上传 → 服务端去重入库 → Admin 更新。发送时管理员指定设备/SIM 和号码；系统记录操作状态；重复事件和网络超时不盲目重发。初版不导入历史短信，不默认 MMS/RCS；双卡模型预留，硬件与系统验证后启用。永久保存业务信息、原样显示，不进行业务脱敏。

### 来电

蜂窝振铃 → 设备通知服务端但保持未应答 → 按已启用设备/SIM 路由呼叫一个目标 → 目标真实接听且媒体就绪 → 复核蜂窝仍振铃 → 设备接听蜂窝 → 双向音频。目标拒绝/超时则不应答；主叫先挂立即取消目标呼叫；用户本机接听则不强制接管。运营商语音信箱和收费行为不作保证。

### QQ/TG 消息外呼

配对用户私聊发送两种格式之一 → 校验身份、号码和唯一 SIM 映射 → 原子占线 → 手机先拨目标号码 → 向同一消息用户回拨平台语音 → 两方实际接听后桥接 → 一方结束时结束另一方。有效消息立即拨号，无二次确认；B 先接而用户未接可计费。推荐超时 B 已接后等 15 秒，用户先接时等待 B 30 秒，已接受推荐、可配置且需实测。结果未知进入对账，不重新拨号。号码未知或重复匹配拒绝，禁止私自选择其他 SIM；紧急号码不能由本系统拨打。

## 5. Admin、配对、设备与安全

单管理员登录管理设备列表、SIM 号码、SMS、通话、QQ/TG 桥账号登录、配对与设备路由、状态/告警。配对用户获得接听和消息拨号完整授权；绑定码使用 CSPRNG、有限期、单次消费及限流，向对应桥账号私聊发送后立即生效。账号登录、消息接收、可主动语音和真实双向音频分别显示，不能互相推定。设备心跳建议 30 秒，90 秒过期为离线、单项状态 TTL 分开；精度需网络实测。

用户决定关闭 CORS、由其自行公网/TLS；CORS 不是认证，单管理员登录、独立设备凭据、一次性码、防重放与限速仍保留。永久保存原始业务数据，不做脱敏；管理员密码、验证码、平台 session 等凭据不应写入源码或公开日志，这不改变用户对业务数据的保存要求。数据不备份意味着故障可能永久丢失。

## 6. 技术与许可证门槛

- 旧的 android-voice-sip-agent 是 GPL 系列并使用 SIP，仅作历史公开原理参考，不能复制代码改标 MIT；KoishiRTC 亦为 GPL-3.0-only，不能假定直接整合后整体 MIT。各运行组件的依赖和分发边界须核查，不因分进程就当然排除义务。
- Shizuku 可无线调试免 Root 启动但重启需重新启动。对目标 ROM 的双向电话音频是否可用、延迟接听是否可控，以及独立 MIT 实现均未实测。
- QQ 与 Telegram 原生一对一拨号/接收音频、消息身份稳定映射及适配器许可证均需逐平台验证；登录和配对不等于语音可用。
- 初期至少三台不代表三通并发，未来 20 台以上也不自动代表 20 通；需实测容量。

## 7. 分期与验收

| 阶段 | 验收 |
|---|---|
| 0 只读环境 | 获取服务器 OS/架构和资源；确认目标手机与账号；不修改服务器 |
| 1 无 SIP/MIT 可行性 | 核定兼容许可证与原生媒体组件；独立真机验证蜂窝来电延迟接听、外呼及双向音频；失败则不能宣称方案可实现 |
| 2 平台 POC | QQ、TG 分别真实验证主动一对一语音、消息、用户身份和双向 PCM |
| 3 APK + Admin | 一业务 APK 加 Shizuku；至少三台绑定、号码与状态、短信收发与断线恢复 |
| 4 通话集成 | 浏览器、来电、QQ/TG 消息外呼和竞态分别验证，手机先外拨再平台回拨 |
| 5 扩展准备 | 20 台以上连接/容量模拟与监控；实际并发指标明确后评估；另经授权部署 |

状态 UNKNOWN 不等于失败/结束；调用已提交不可盲重拨。测试包含消息重放、双卡变更、平台掉线、主叫取消、两端接听竞态、双向真实收听及费用观察。

## 8. 尚缺的事实和技术验证

手机型号/ROM/运营商；Local-server OS/CPU/内存和端口；QQ/TG 账号和服务器 CPU 兼容性；真实同时通话数；号码默认国家/地区；浏览器可用安全上下文；无 SIP 且 MIT 的电话/平台音频完整实现。接受推荐不等于上述事实已经提供。详见 [未确认与验证清单](未确认与验证清单.md)。
