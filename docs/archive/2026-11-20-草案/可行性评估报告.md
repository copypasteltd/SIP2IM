## 1. 总体结论

| 模块 | 可行性 | 一句话判断 |
|---|---|---|
| Admin 后台、设备绑定/状态、单管理员 | **高** | 常规 Web 工程，无技术未知数 |
| 短信收发（新短信、单条发送） | **高** | Android 公开 API；侧载 APK 不受 Google Play 短信权限政策约束 |
| 手机↔服务器信令与音频传输（无 SIP） | **高** | 自建 WebSocket/UDP + Opus 即可；去掉 SIP/PBX 反而简化架构 |
| 手机蜂窝通话双向音频（免 Root、无外设） | **有条件可行，取决于机型** | 机制存在且有公开实例，但每台设备必须单独验证 |
| 来电“目标未接则不应答” | **高（逻辑层）** | 应答动作由 APK 发起，未接时不调用接听即可；运营商行为不在控制内 |
| 消息触发外呼（先拨蜂窝，再回拨） | **高（逻辑层）** | 依赖平台回拨与手机音频两个前提 |
| 浏览器实时通话 | **中高** | 技术成熟；唯一硬约束是浏览器麦克风需要安全上下文 |
| Telegram 原生一对一通话桥接 | **中低** | 需普通用户账号 + 原生通话库；社区有 POC，无成熟成品 |
| QQ 原生一对一通话桥接 | **低，风险最高** | 无官方接口；唯一路线依赖非官方客户端注入，且现有实现为 GPL、仅 ARM64 验证过 |
| 20 台以上规模 | **设备连接：高；并发通话：受平台账号限制** | 见第 4 节，是本次评估发现的关键约束 |
| 整体 MIT 开源 | **可行，但须独立实现** | 不能复用 GPL 上游代码；可依赖 MIT/BSD/Apache 及动态链接的 LGPL 组件 |

**总判断：** 短信 + Admin + 设备管理 + 浏览器通话这一核心部分**可以落地**，前提是测试手机通过音频门槛。Telegram 桥接**可尝试**。QQ 桥接**不能承诺**，建议放在最后，并准备接受其失败。

## 2. 关键技术点逐项分析

### 2.1 手机通话音频（整个语音功能的总闸门）

- **机制：** Android 13 起提供通话音频拦截系统接口（下行提取 AudioRecord、上行注入 AudioTrack），需要 CALL_AUDIO_INTERCEPTION 等特权。shell 用户（uid 2000）持有这些权限，Shizuku 可让 APK 以 shell 身份运行受限代码。这是 **Android 平台机制，与 SIP 无关**；去掉 SIP 不影响音频可行性。
- **证据：** 上游作者报告 Pixel、Motorola 双向音频可用，社区报告 5 台小米/vivo/三星等在特定模式下双向可用，另有设备仅单向或未测试。[上游 README](https://github.com/sparkcyf/android-voice-sip-agent/blob/main/README.md)、[作者实现说明](https://blog.sparktour.me/en/posts/2026/10/10/android-shizuku-cellular-sip-gateway/)
- **限制：** 依赖隐藏 API 与厂商音频 HAL 是否声明通话收发路由；系统升级可能失效；普通捕获权限不能证明上行注入可用。实际可用版本基本以 **Android 13 及以上**为主，更低版本需单独验证。
- **MIT 影响：** 可依据 AOSP 公开接口独立实现（clean-room），**不得复制 GPL 上游代码**。
- **判断：** 机制可行，**逐台 go/no-go**。建议首批 3 台优先选择已有成功报告的机型及 Android 13+。

### 2.2 呼叫控制

来电接听、挂断、外拨通过 Telecom/InCallService 实现；上游以 shell 权限设置 companion 模式，使网关不必取代默认拨号器。**延迟接听可控**：APK 只在收到“平台已接听”指令后才调用接听。紧急号码由系统限制，本系统不能用于紧急呼叫。

### 2.3 Shizuku 运维

Android 11+ 可通过**无线调试**免 Root 启动，但**每次重启需重新启动**；无线调试本身需要设备连接 Wi-Fi。上游反馈部分 MediaTek/传音机型的 Shizuku 13.6.0 无法启动，需降级 13.5.4。专机常开可接受，但需在 Admin 中把“Shizuku 未运行”作为独立告警。远期可评估把无线调试自启动逻辑内置到业务 APK（技术可行但复杂度高），实现真正单 APK。

### 2.4 无 SIP 传输

手机 ⇄ 服务器使用自定义协议：控制走 WebSocket，音频走 WebSocket 二进制帧或 UDP，编码 Opus（libopus 为 BSD，可与 MIT 项目共存）或 PCM。需自行处理抖动缓冲、时钟漂移、断线重连；工程量中等，无原理障碍。

### 2.5 浏览器通话

服务端 WebRTC 候选：Pion（Go，MIT）或 werift（TypeScript，MIT），依赖许可证需逐项核查。WebRTC 媒体的 DTLS-SRTP 是协议内建、自动协商，**不需要项目配置证书**，与“项目不配置 TLS”不冲突。**硬约束：** 浏览器只在 HTTPS 或 localhost 下允许麦克风。内网阶段可选：①用户自建 HTTPS 代理；②在访问用 Chrome 上为该内网地址开启 `unsafely-treat-insecure-origin-as-secure` 选项（仅限测试/自用电脑）。

### 2.6 Telegram 桥接

- Bot API **无法**发起或接听语音通话；必须用**普通用户账号**（MTProto，如 Telethon，MIT）。
- 一对一通话媒体需原生库（如 ntgcalls）；该库许可证尚未直接核实到原文（抓取失败），初步了解为 LGPL 系列——若属实，以独立进程/动态链接方式使用可与 MIT 项目共存，但不能并入改标。
- 社区存在一对一双向 PCM 的 POC，但主动外呼、长期稳定性未见成熟验收。
- 服务器为 x86_64，Telegram 原生库通常支持该架构。
- **判断：中低**，作为第一个平台验证对象。

### 2.7 QQ 桥接

- QQ 官方机器人接口只有消息能力，**没有一对一语音通话接口**。
- 唯一已知路线：Linux QQ 官方客户端 + NapCat + AVSDK 注入宿主，通过虚拟音频设备收发。现有实现（KoishiRTC 等）为 **GPL-3.0-only**，且项目方仅在 **Linux ARM64** 上验证主动私聊通话；**你的服务器是 x86_64**，属于未验证组合。
- MIT 约束下必须独立重写注入宿主，或把 GPL 组件作为可选独立插件（则整体不再是纯 MIT）。
- 依赖专有客户端特定版本，QQ 升级即可能失效；自动化操作有**账号封禁风险**。
- 服务器缺少 PulseAudio（需安装），已有 Xvfb。
- **判断：低**。建议明确接受“QQ 可能最终不可实现”的结果。

## 3. Local-server 只读探测结果

| 项目 | 结果 | 影响 |
|---|---|---|
| 系统 | Ubuntu 22.04.5 LTS，内核 5.15 | 与方案目标一致 |
| CPU | x86_64，Intel i5-12400，可用 8 个处理器 | 信令与音频转码绰绰有余；QQ 路线架构未验证 |
| 内存 | 62 GiB，可用约 51 GiB | 可容纳多个 QQ/TG 客户端实例 |
| 磁盘 | 根分区 98 GB，**已用 90%，剩余约 9.7 GB** | **风险**：永久保存 + 无备份 + QQ 客户端安装，空间偏紧 |
| 已有软件 | node/npm、python3、psql、java、ffmpeg、Xvfb；docker 已安装（按约束不使用） | 可原生部署；PulseAudio 未安装 |
| 系统状态 | systemd 状态为 degraded | 有服务处于失败状态，部署前需查明，避免误判 |
| 端口 | 已有大量服务监听（含 15100、384xx、25565、多个本地数据库/缓存端口等） | 新服务需选未占用端口；不得触碰现有数据库与服务 |

SSH 连接使用了密码库中的 Local-server 条目，并固定校验已知主机密钥。凭据未写入日志或对话。

## 4. 关键约束：平台账号决定并发上限

一个 QQ/TG 账号通常**同一时间只能处于一通语音**中（Telegram 用户账号的并发通话能力未核实，按单通设计更稳妥）。当前已接受的推荐是“每个平台一个专用桥账号”，因此：

- **全系统最多同时 1 通 QQ 桥接 + 1 通 Telegram 桥接**，与手机数量无关；
- 20 台手机同时来电时，超出的来电只能拒绝或改由浏览器接听；
- 消息外呼回拨同一用户时，若该用户已在通话中，回拨会失败。

扩容方式只有一种：**增加桥账号数量**，每个账号对应一个独立客户端实例。服务器内存足够，但需要更多账号、更多登录维护，QQ 侧封号风险同步放大。**这一点需要你决定期望的平台并发数。**

## 5. 你的选择带来的残余风险（已接受，记录在案）

| 选择 | 残余风险 |
|---|---|
| 配对码即生效 + 完整授权 + 消息即拨号 | 配对码泄漏 → 他人可直接用你的 SIM 拨打任意号码，产生话费；建议保留号码前缀限制与单日次数上限（已在推荐中） |
| 关闭 CORS + 项目不配置 TLS | 内网中其他设备可以跨站调用 API；管理员会话与设备认证必须严格；公网转发前务必加 HTTPS |
| 永久保存、不脱敏、无备份 | 数据长期集中；磁盘仅剩约 9.7 GB；故障即永久丢失 |
| 先拨蜂窝再回拨 | 被叫先接而用户未接时会计费 |

## 6. 实施门槛（按顺序，任一不通过即调整方案）

| 门槛 | 验证内容 | 不通过时 |
|---|---|---|
| G0 设备音频 | 第 1 台手机：Shizuku 启动、来电延迟接听、外拨、双向真人可听 | 换机型；连续失败则语音功能整体不可实现 |
| G1 传输与浏览器 | 无 SIP 自建传输 + 浏览器 WebRTC，手机↔浏览器双向通话 | 调整编码/抖动处理 |
| G2 Telegram | 普通账号一对一主动呼叫 + 双向 PCM（x86_64） | 平台桥接暂只保留浏览器 |
| G3 QQ | x86_64 上 QQ 客户端 + 独立实现的 MIT 注入宿主，一对一主动呼叫 | 放弃 QQ 或接受 GPL 可选插件（需你决定） |
| G4 规模 | 3 台真机 + 20 台以上模拟连接；平台并发按账号数验证 | 调整账号数与路由策略 |

短信与 Admin 可以与 G0 并行开发，不受语音门槛阻塞。

## 7. 需要你决定或提供的事项

1. **测试手机型号与 Android 版本**（最关键；建议 Android 13+，优先已有成功报告的机型）。
2. **平台并发数**：每个平台准备几个桥账号？（决定同时可桥接几通）
3. **QQ 失败预案**：若 MIT 约束下 QQ 无法实现，是放弃 QQ，还是允许 GPL 组件作为可选插件？
4. **默认国家/地区与允许拨打号段**。
5. **磁盘**：是否为本项目清理或扩容磁盘（当前剩余约 9.7 GB）。
6. **浏览器安全上下文**：内网测试期使用 HTTPS 代理还是 Chrome 内网例外选项。
