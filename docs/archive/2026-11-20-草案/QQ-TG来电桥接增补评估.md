# QQ / Telegram 来电桥接方案（无 SIP）

> 2026-11-20 现行需求稿；手机直接媒体及 QQ/TG 适配尚未实测；禁止将历史 SIP 参考方案作为现行实现。

## 需求与目标

SIM 来电时，手机继续振铃且不接听；系统依据设备/SIM 路由，向已配对 QQ 或 Telegram 用户发起原生一对一语音。目标真实接听、媒体准备就绪且主叫仍振铃后才指示手机接听，双方建立实时音频；若目标未接、拒接或超时，则手机不应答。运营商语音信箱与费用不作保证，实机检查。

每个 SIM 首版一个主目标，一个目标可绑定多设备；不并行、不自动备用；初始平台振铃 20 秒可配置。系统先各平台使用一个专用桥账号；已配对用户直接获得接听及消息外呼完整授权，不需管理员复核。

## 逻辑架构

蜂窝主叫 → 安卓手机/SIM + Shizuku 通话控制和音频适配 → 自建无 SIP 连接/会话协调器与媒体桥 → QQ/TG 原生通话适配器 → 配对用户；浏览器来电路由为同级可选目标。服务采用用户服务器原生进程，禁止使用 Docker、WSL 或外置硬件。上述适配器是拟开发能力，MIT 许可兼容和各平台真实呼叫尚未验证；GPL 历史候选不能直接改标 MIT。

## 严格时序

NEW → CELLULAR_RINGING → PLATFORM_DIALING → PLATFORM_CONNECTED → MEDIA_READY → ANSWER_REQUESTED → CELLULAR_CONNECTED → BRIDGED → TERMINATING → ENDED；失败进入 FAILED，结果不明进入 RECONCILING/UNKNOWN。

1. 设备报告真实来电，携带 device_id、sim_id、call_id、event_id；服务端持久化、去重、占线。
2. 路由已配对的真实平台用户并发起一次平台拨号，记录 call_id；不能以消息、排队或本地回执视为接听。
3. 目标真实接听，确认平台媒体端点准备就绪，并再次确认蜂窝仍在振铃；之后才提交手机接听命令。
4. 设备报告蜂窝通话真正 ACTIVE；任一步失败或状态未知不得虚报成功；两方向建立音频并在实测中验证对方听见。
5. 双方任一挂断立即清理另一方；结果未知依据原 ID 对账，不盲重拨，保留锁至可确认或人工处理。

目标先接与主叫取消之间存在异步竞态，不承诺绝无短暂窗口；平台接听后手机接听失败需迅速终止平台通话。本机人工抢先接听时不强制接管并取消平台腿。平台不接、拒绝或超时时停止平台呼叫，手机不发送应答；用户已表示无需围绕其他运营商细节增加产品策略，但测试仍需如实记录。

## 验收

| 场景 | 证据及结果 |
|---|---|
| 未接/拒接/超时 | 平台呼叫结束，手机 Telecom 状态未进入 ACTIVE；全程事件带时间与 ID |
| 目标接听 | 平台接听证据早于设备接听请求和蜂窝 ACTIVE；两个方向真人可辨识 |
| 主叫取消/接听竞态 | 不接已终止电话；终止或对账平台腿，无盲重拨 |
| 电话先挂/平台先挂 | 对侧结束，媒体及设备锁清理；未知状态不得伪报已结束 |
| 手机与平台重启 | 恢复状态或人工介入，不凭重复事件重新呼叫 |
| 设备规模 | 至少 3 台真机入站路由；20 台以上连接与容量模拟，平台和媒体能力需各自实测 |

配对权限、原样保存和单管理员以 [Admin 方案](Admin管理体系与设备运营需求.md) 为准；服务未配置 TLS、CORS 按用户要求关闭。是否具备可用无 SIP/MIT 平台适配器和真机音频能力仍为实施门槛。
