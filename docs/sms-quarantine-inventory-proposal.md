# SMS quarantine inventory: staged proposal

Status: isolated prototype only. No route or UI is registered, no migration is created, and no ingestion, custody, replay, retention or notification is implemented. Existing systems do not populate a quarantine table. The decoder sees schema-parsed JSON, after unknown fields have been stripped; bytes do not preserve the original JSON wire representation or PDU data. UTF-16LE JSON v1 preserves the represented post-parse string code units. No multi-writer or single-instance safety is established.

## Proposed dependency table and read contract

A separate reviewed migration would define an immutable table with UUID primary key, non-null creation timestamp, device and event identifiers, reason, encoding/version, byte length and bounded bytea payload (the prototype rejects over 262144 bytes; this is an unvalidated read limit, not an ingestion capacity guarantee), plus a descending (created_at, id) index. Constraints must verify length and encoding, and authorization, retention, provenance and integrity must be agreed before deployment. The UUID is a quarantine-record ID, distinct from the existing device event ID. The ordering tuple must never change. A 65536-byte wire frame can expand beyond 65536 bytes in UTF-16; future custody must derive and test an adequate bound, and reject without ACK or data loss when capacity is insufficient. No truncation is allowed: inventory exposes oversized row metadata; export returns 413 for rows above the prototype bound. The future audited reader must enforce the size bound in SQL before allocating payload bytes and return metadata alone for oversized records. Inconsistent rows fail closed. Pages contain at most 50 records; keyset cursors preserve PostgreSQL timestamp precision. Concurrent inserts ahead of a cursor are not a snapshot; export is by explicit quarantine record UUID, not a complete archive. Cursor timestamps follow the finite four-digit PostgreSQL year format validated by the prototype.

The injected auditAndRead implementation must authenticate an administrator via the existing session service, write an access audit identifying actor, mode and page boundary, read the page, and commit atomically before returning any data. It must use parameterized SQL, avoid logging payloads or bearer tokens, and return no bytes for inventory. An audit failure, missing table or query failure must return an error and disclose no records. Do not wire the module until this implementation, schema and custody semantics are separately reviewed and tested with PostgreSQL. Authenticated GET responses, including errors, use no-store. Export payloadBase64 is the exact stored bytea, labelled json-utf16le-v1 and length; it may contain sensitive information. Downloads require authenticated fetch and controlled handling. API cursors are untrusted input, not authorization or snapshots.

The isolated PostgreSQL reader prototype and proposed schema live in core/src/db/sms-quarantine-reader.ts and docs/prototypes/sms-quarantine-reader.sql; neither is wired or migrated. It confirms actor existence, but the staged contract provides only actor ID, not session proof. Authentication is a request-start decision: a session revoked after that decision can still complete a read. Exact session revalidation needs a reviewed contract change. Audit insertion, bounded read, and confirmed commit use one transaction; missing and oversized exports are also audited. Commit uncertainty returns no records. The proposed dedicated audit table is separate from the existing audit log and is not exposed by its API. Export uses FOR SHARE, which requires appropriate PostgreSQL locking privileges in addition to SELECT. The proposed event foreign key assumes a safe device_event marker parent that does not yet exist; its compatibility with future custody is unresolved. Proposed foreign keys do not prove the event belongs to the stated device or has an SMS type; immutable ordering also requires enforcement. The audit page_limit is the reader's requested row count, including the inventory lookahead, not the displayed page size. PostgreSQL char_length counts characters, while the reader limits JavaScript UTF-16 code units; supplementary characters can therefore pass the schema and fail the reader. Fake tests cannot establish PostgreSQL locking, query evaluation, permissions, or durability.

No raw or parsed SMS content is included in inventory. Export does not support mutation, repair, or reprocessing. A future production design must settle access auditing, retention, device authorization, duplicate handling, transaction/ACK semantics, storage limits and multi-writer safety before ingestion is connected. Unit tests with fakes do not verify database semantics or custody.
