# Experimental call generation identity

**Current runtime limitation:** the shared parser accepts `callGeneration: true`, but Core discards the hello capability and does not bind call handling to `generation`. No generation-aware call path or runtime enforcement is enabled. Devices must not advertise this capability until the full contract below is implemented and verified.

Protocol v1 permits an optional hello capability `capabilities.callGeneration` and optional `generation` fields on cellular call events and commands. The value is a canonical `gen_` ULID; the identity is the tuple (authenticated device ID, callId, generation). Existing v1 frames without either field remain valid. A missing or false capability is unsupported; a field alone does not negotiate a feature. Existing parsers may silently strip unknown fields. Never send generation-dependent commands to a legacy peer or assume a peer recognized a field.

This is a wire-format foundation only. No current device advertises or implements this capability, and no real call action is enabled by it. A true declaration is not evidence that a platform offers safe call-specific control.

Before enabling it, a future device implementation must create a fresh generation for each distinct call incarnation, keep it stable on every event for that incarnation (including replays and terminal events), and never reuse it across restart or callId reuse. Missing, malformed, inconsistent, or unbound generation must fail closed. Outbound dial needs a generation allocated and reserved before dispatch, with all subsequent events bound to that reservation; uncertain outcomes must not be retried as a new call.

Capability is scoped to the authenticated live connection and must be re-established after reconnect; neither a stale snapshot nor an incoming generation substitutes for negotiation. Core must retain the full identity through durable events, sessions, intents and retries, compare it when replaying out-of-order events, and fence stale connections. Legacy callId reuse remains quarantined. Capability loss or ambiguity cannot downgrade an in-flight operation to callId-only.

At execution, the device must atomically resolve and verify the exact (callId, generation) against the live platform call immediately with the platform-specific call action. A check before enqueueing, or a check followed by an unbound global action, leaves a race in which another call can replace the target. If the platform cannot provide that atomic association, the action remains unsupported; no fallback to a global action is allowed. A mismatch, missing call, restart, or uncertain outcome must never act on another call. ACK success proves only the documented command acceptance, not a completed call transition; only matching generation events may establish state.
