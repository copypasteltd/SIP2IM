# Proposal: retry-safe Android device binding

**Status: design for review, not an implemented contract.** This proposes a protocol and database change; the authoritative contract remains [05](开发约束文档/05-接口契约实现细则.md), and [06](开发约束文档/06-数据库与迁移规范.md) remains authoritative for schema until the corresponding change is synchronized. This document records a proposed design; its existence does not indicate that implementation, migration, service operation, or deployment has occurred.

## Problem and existing constraints

Today [BindingClient](../android/app/src/main/kotlin/io/voipgw/gateway/core/BindingClient.kt) receives a server-generated token and persists it only after the response. [BindingRepository](../core/src/devices/binding.ts) consumes the code and creates the device and credential in one transaction. A lost response, process death, or failed local save after commit therefore leaves a consumed code and a device whose token the phone lacks. The transaction helper explicitly represents an uncertain COMMIT ([pool.ts](../core/src/db/pool.ts)); a timeout or subsequent rollback cannot prove non-commit.

Preserve the six-digit, ten-minute, single-use code; separately generated codes do not invalidate one another. Preserve admin authorization to create codes, existing per-IP failure limit (ten failures per minute), device revocation, independent credentials, disabled-by-default calling, and no automatic takeover based on a phone number. Store only SHA-256 token/code hashes on the server, never plaintext credentials in logs, URLs, fixtures, or conversation. Preserve the HTTP-only/no TLS and open CORS constraints, minSdk 19, and existing non-deletion policy ([global constraints](开发约束文档/01-全局开发约束.md)). These requirements limit the security achievable here.

## Proposed wire contract

Use a **new explicit endpoint** `POST /api/device/bind-v2`, not an optional field on the old endpoint. The existing Zod schema ignores unknown fields, so a new client sending an extension to the old route could be silently accepted while the old server generates a different token. Never negotiate by treating an ambiguous response or 404 from a possibly intercepted endpoint as permission to fall back to legacy binding.

The client generates 32 independent CSPRNG bytes and encodes them as canonical unpadded base64url (43 characters). Send this exact credential once per attempt in `Authorization: Bearer <credential>`; request JSON contains the existing code and metadata fields. Validate exact encoding and decoded length. The request also contains `protocolVersion: 2` and a client-generated, independent 128-bit random `attemptId` (canonical encoding, persisted with the pending record); the response contains `{ data: { protocolVersion: 2, attemptId, deviceId } }`, never the credential. The client checks the exact version and attemptId against its pending record before accepting success; the echo correlates responses but is not server authentication under HTTP. Both request and response require no-store; do not redirect, include credentials in URLs, or log headers, bodies, exceptions containing request objects, traces, proxies, analytics, crash reports, or database parameter values. Metadata is bounded and validated. Code stays in the existing request body, and must also be excluded from logs. No literal credentials or codes in fixtures.

The credential is both the eventual bearer credential and the replay key; it is secret, not a public idempotency key. Its SHA-256 digest is an index, never returned as an authenticator. An exact replay means same code, same credential, same attemptId, and the same normalized immutable metadata captured in the initial pending request; conflicting metadata must not mutate the device or return success. Define an unambiguous versioned canonical encoding and compare stored request fingerprint; do not fingerprint the six-digit code alone as though it were secret.

## Client durable state machine

1. After explicit local user confirmation and origin/code validation, create a fresh credential and freeze the origin, code, protocol version, attemptId, local identity generation, and normalized request metadata in a single private pending record. Persist and verify the complete record durably **before opening the network connection**. A failed or uncertain save means do not POST; do not generate a replacement until local state is reconciled. Serialize attempts locally to avoid double taps and process races. Keep app backup disabled. Private app storage is not hardware-backed protection and does not defend against a rooted/compromised device.
2. POST the exact stored request and credential to the exact stored origin; no redirects. Restart, timeout, crash, malformed response, unknown HTTP error, and uncertain local writes leave the record pending. Retrying uses the *same* values. UI must show outcome unknown, not claim failure or create a new device. Use bounded backoff; user can resume. Never store the pending secret in an intent, deep link, or notification.
3. The credential becomes usable on the server at commit, **before** local promotion; a lost response or local failure can therefore leave an active orphan. Do not treat pending as a harmless draft or expose it to the running gateway. On a valid correlated success, atomically compare-and-swap the durable pending record: promote only if its attemptId and generation still match and its status remains pending, then durably write the credential, origin and returned deviceId as active and remove pending state in the same recoverable local transaction. Before requesting abandonment, durably advance the generation and mark the attempt cancelling; any delayed success, retry worker or callback must fail this CAS and cannot reactivate it. Retain its credential and evidence until server cancellation is confirmed. Verify durable state before starting the gateway. If persistence fails or the app dies, keep/recover pending state and replay, rather than generate a new credential. A crash between local writes must not result in a partially active identity; one atomic record or journal with recovery is required. The stored code is needed for retries and is removed on promotion.
4. A definitive invalid/expired response is actionable only after the server's transaction semantics below rule out an in-flight/previous commit for this key; otherwise retain unknown and ask the administrator to reconcile. Never automatically clear a pending credential and bind again. Explicit abandonment requires the administrator cancellation fence described below; local deletion or a visually absent device is insufficient, because an earlier POST may still commit later. After uninstall, restore, storage corruption or key loss, do not infer ownership from device hardware, SIM, or phone number; administrator revokes/rebinds and explicitly associates history if appropriate.

## Server transaction and replay

Add nullable replay evidence to the existing code row (version, attemptId, credential hash, immutable request fingerprint, and replay deadline), plus a persistent cancellation tombstone; old rows remain legacy/unkeyed. Use a new forward migration, preserve existing records, and enforce internal all-or-none constraints for v2 evidence. The existing globally unique `device_credential.token_hash` prevents one token from owning multiple devices. Keep the code row and replay evidence; C-09 forbids automatic deletion of business records. Deadline limits acceptance, not retention.

Within one database transaction, look up the hash of the supplied six-digit code and lock its row `FOR UPDATE`. Every v1 and v2 bind and replay path must first reject a tombstoned row before inspecting unused or used state. When acquiring multiple existing rows, all bind, replay, cancellation and revocation paths use the global order **code → device → credential**, locking multiple rows of each kind in stable primary-key order; operations starting from a device must locate associated code IDs first without locking, then lock and revalidate in that order, retrying on changed associations. Lock timeouts or deadlocks yield unknown, never success or presumed rollback. While holding the code lock:

- For an unused, unexpired code: enforce validation and existing limits, insert one device (normal defaults), insert the supplied credential hash, and set used time, device reference, version, fingerprint, attemptId and replay deadline together. Set the replay deadline to code expiry plus 24 hours as a **proposed review value**, recorded in the same transaction. Return success only after confirmed commit.
- For a v2-used code: even after code expiry, return the original deviceId only if credential digest, attemptId and frozen fingerprint match, the deadline has not passed, and the linked device and credential still exist and are not revoked. Do not update metadata, issue another credential, or create another device. Serialize the revocation check with revoke using the global row-lock order; revocation wins after it commits and replay must never resurrect a revoked credential. Disabled but not revoked devices may replay the identity without changing enabled/paused flags.
- Any different credential, different fingerprint, legacy-used row, revoked identity, or expired replay window returns a generic failure without revealing the deviceId or whether a code was used. Unknown and expired unused codes retain the existing documented 400/410 behavior if compatible with the approved error contract. Apply existing rate limits to failures including mismatches; bound successful replay traffic too without weakening the existing failure limit. In-memory per-process/IP limits are not shared across processes and reset on restart: multi-instance enforcement needs a separately designed shared limiter.

A unique-credential conflict on initial insert rolls back the **whole** transaction; return a generic failure, never attach the code to the conflicting identity or consume it. A transaction error, lost COMMIT acknowledgment, or release failure is outcome **unknown**: do not internally create a fresh token or code. The same client retry obtains the original result if committed, or creates it once if not committed, provided the code is still valid. A retry that reaches an unused code after its expiry cannot prove an earlier attempt never committed if an earlier transaction is still in flight: lock/wait for it to settle on the authoritative primary, or return unknown on timeout. Database failover, replica lag, or incomplete durability must not be interpreted as absence; require a settled authoritative consistent read and durable commit policy. If replay expires before the phone can resolve the result, retain uncertainty and require admin reconciliation; never silently rebind.

### Cancellation fence and response uncertainty

Provide an administrator-authenticated cancellation operation, with its precise route and error vocabulary subject to protocol review. At creation, assign each code row a stable opaque random record ID distinct from the six-digit code, and expose it only through authenticated administrator views, so an administrator can select and cancel the record even when the phone and plaintext code are lost. The ID identifies a record, not authorization or proof of device ownership; inventory and review any ambiguous legacy records, and require existing admin authentication and explicit selection. Do not log the code; a code hash is not a secret. Adding the ID and admin view is a proposed schema/API change requiring review. On the authoritative primary the cancellation transaction takes the same code-row lock as bind. If unused, durably tombstone the code, making all later v1 and v2 binds fail. If already bound, atomically tombstone it and revoke its device and credentials using the global code → device → credential lock order. Post-commit, run the existing session/media teardown, with failures tracked for retry; authorization must already deny the revoked identity. Do not delete the row. A late bind either commits first and is then revoked, or sees the tombstone and cannot commit. A cancellation timeout, unknown COMMIT, unavailable primary, missing code row, failover uncertainty, or failed cleanup is not proof of cancellation: retry/reconcile the same authenticated operation; keep the client pending and do not authorize replacement until a committed fence and required teardown are confirmed. A matching server response can be lost and must be safely repeatable. Existing v1 binding code must also honor the fence; a legacy server after downgrade cannot be trusted to enforce it, so block downgrade while fences or attempts can be outstanding.

For an attempt never sent, a validated client-side rejection can be definitive. Once any POST may have been sent, a later 400, 410, 429, unsupported route, malformed response, or network error alone does **not** prove an earlier attempt failed; limits may reject before the row lock and a generic rejection may hide an existing binding or replay-window expiry. Keep the original credential and unknown status until a matching replay succeeds or administrator cancellation/reconciliation establishes a durable fence. An expired-code reply may be definitive only with an explicitly specified, authenticated authoritative result that serializes against the original transaction and rules out prior commit; this proposal does not assume existing generic errors provide that proof. Under cleartext HTTP, even a correctly echoed response can be forged.

### Rebinding and local generation boundaries

The current [GatewayService](../android/app/src/main/kotlin/io/voipgw/gateway/core/GatewayService.kt) captures credentials in socket callbacks, and [Outbox](../android/app/src/main/kotlin/io/voipgw/gateway/core/Outbox.kt) has no identity column. Rebinding must first quiesce the old service: stop accepting commands and side effects, cancel reconnects/timers, close the old socket and fence all asynchronous callbacks by a monotonically advanced, durable local identity generation. A socket callback or ack from an old generation cannot mutate new-generation state, issue commands, or flush data under the new identity. A delayed OS callback with verifiable old-generation provenance may only durably update its quarantined old-generation result record; it must not trigger a new action, send under the replacement identity, or be discarded merely because the generation changed. Unknown provenance remains quarantined for reconciliation. Generation, pending/active identity and the fence must recover consistently after process death; the gateway starts only from a complete committed active record. Revoke the old server identity via the authorized admin flow, observing uncertain outcomes and connection teardown, before enabling the replacement; do not assume a socket close alone revokes credentials.

Namespace outbox events, command ledger, SMS tasks/results, acknowledgments, and other device-scoped state by immutable old/new identity generation. Old queued work cannot be sent or executed as the new device; preserve it in a quarantined old namespace for explicit reconciliation without deleting business history or automatically retransmitting uncertain external actions. In-flight SMS/call results must retain original provenance and unknown outcomes, not be assigned to the replacement. Existing unscoped rows cannot safely be assumed to belong to a new identity: inventory and migrate only with proven ownership; otherwise quarantine. This requires a separately reviewed migration and a way to quiesce producers across process death; until then block rebinding rather than mix identities.

## Compatibility, adoption, and recovery

Deploy an additive server that supports both routes before any v2 client; v1 keeps its existing response and limitations and never receives a v2 replay result. A new client uses only v2, verifies a well-formed v2 response and persists its pending request before sending. On an old server, an unsupported route is an upgrade-needed state only when no earlier POST for that attempt could have been accepted. After any uncertain send, an unsupported route leaves that attempt pending and unknown; do not fall back automatically or clear its credential. Old apps continue legacy behavior until explicitly retired. Do not assume adoption, deployed schema, or fleet versions: inventory actual clients and server versions, establish support dates and rollback policy before enabling. A downgrade after a v2 POST leaves an unresolved pending identity; restore a compatible server or use administrator reconciliation. Do not delete the new replay evidence on rollback.

Existing active v1 credentials remain valid and are not replaced on client upgrade. Existing used codes lack matching replay evidence and must never be retroactively assigned one. If a legacy response was lost, the server has only a hash and cannot recover the plaintext: administrator identifies and revokes the orphan if possible, creates a new code, and binds as a new identity. The available device metadata is not proof of ownership; if identification is ambiguous, preserve uncertainty rather than revoke or merge automatically. The existing permanently unique hash of a six-digit code also means eventual code-space exhaustion under no-deletion retention; do not silently reuse a hash or conflate generations. A separately reviewed generation/retention design is required before exhaustion.

## Threats and explicit limitations

- **Cleartext transport:** HTTP exposes both code and bearer credential to passive observers and allows active modification, impersonation, and theft. This proposal cannot provide confidentiality or server authentication on an untrusted network. The existing open CORS policy and user-directed HTTP origin widen exposure: hostile web pages can make cross-origin requests under the permissive policy, including authorization-bearing requests where preflight allows them; browser/network controls and unknown credentials may limit a particular attack but are not server authentication or a substitute for authorization; restrict operation to an appropriately trusted network operationally, while recognizing that this is not cryptographic protection. Changing transport or CORS requires a separate authorized change.
- **Six-digit code:** only one million values; online guessing remains possible. Rate limiting and short validity reduce but do not eliminate risk; code hashes are trivially enumerable after a DB leak. Capturing a code before first use lets an attacker bind with their own credential. Keyed replay prevents a different credential from recovering an already consumed binding, not first-use theft.
- **Credential compromise:** possession is sufficient to authenticate and replay; network capture, logs, rooted devices, or insecure diagnostics can leak it. Revocation blocks subsequent replay and normal authentication. SHA-256 storage protects random 256-bit tokens against practical offline preimage search, not code hashes. Exclude logs at every layer and test the deployed configuration.
- **Collisions:** 256-bit random credential collisions are negligibly probable but are still handled by the unique constraint and full rollback. Code collisions are frequent relative to the small space and are retried during allocation; permanent hash uniqueness can exhaust that space. A digest collision must never be resolved by silently attaching another device; treat any conflicting identity as an integrity incident. Do not depend on metadata, ULID timing, or IP as authentication.

## Implementation decisions and verification plan

Implementation must resolve and record: endpoint/field and response changes against authoritative 05 and E-14 error vocabulary; additive schema constraints and 06 migration; exact replay window and behavior after deadline; origin trust and cleartext exposure; shared rate limiting; fleet adoption and downgrade/rollback support. Synchronize the authoritative contracts as the implementation evolves and preserve the existing user security policy.

Acceptance tests should exercise parallel same-code/same-key requests yielding one device and identical ID; different keys or changed metadata yielding one winner and no disclosure; unique-token collision rollback; replay after code expiry within window and denial after deadline; revoke/replay and cancellation/late-commit races, including lost cancellation acknowledgments, cancellation followed by delayed success/local CAS, code loss with admin record-ID selection, universal v1/v2 tombstone enforcement and lock-order deadlocks; forged or mismatched version/attempt echoes; active-server/pending-local crashes; stale socket callbacks and acknowledgments after rebind, including legitimate old-generation OS results confined to quarantine; quarantined unscoped outbox and SMS tasks; malformed input, limiter and secret-free logs. Inject failures before local persistence, before POST, before COMMIT, lost COMMIT reply, release failure, response loss, and crashes during promotion. Test authoritative-primary recovery and failover ambiguity, including no retry with a new key. Verify v1 client/v2 server, v2 client/v1 server, upgrade, downgrade and legacy lost-response flows, and that normal existing credentials survive. These are proposed future checks, not tests run for this document.
