# 平台消息身份与持久化：待实现契约

> 状态：技术提案，未接入真实消息；具体字段和迁移须按各适配器及平台实测确认。

## 已发现问题

现有 platform_inbox 主键为 (platform, platform_message_id)。Telegram TDLib 官方文档将 message id 描述为“在所属聊天内唯一”：[TDLib message](https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1message.html)；本轮官方页面未直接抓取成功，相关描述可由 [Telegram 维护的 issue](https://github.com/tdlib/td/issues/2907) 中的引用佐证。该说明不能直接证明 Telethon/MTProto 原始整数与 TDLib 数值表示完全一致，也不能证明跨账号唯一。

当前 Telegram adapter 发送 event.id 和 senderId；Core 收件箱未保存明确 bridge-account 身份及 typed peer。多账号、跨聊天、账号替换或平台自身 ID 复用下，同一数字可能误去重或冲突。当前 Runtime 对 message.received 返回 CAPABILITY_UNSUPPORTED，避免以不可靠键执行真实操作。

## 设计候选

稳定键需包含：部署环境/平台、桥账号已验证身份、会话或 typed peer 类型与 ID、消息命名空间（已发送/暂态）、平台服务端消息 ID。各适配器只发送它们能从可信平台事件确证的字段；不使用昵称/手机号猜测身份；空值、暂态 ID 或作用域不明时拒绝业务执行并记录可审查状态。建议统一 versioned identity 对象并为不同平台明确字段、限制、编码和唯一索引，具体方案尚未确定。

## 恢复语义

- 提交持久化收件后再 ACK 仅说明收到消息，不代表完成配对或外部操作。
- 对应配对结果、收件完成、通知和操作意图应同一事务；外部电话/SMS 结果不确定必须对账，不自动重试。
- 同键不同 payload 为碰撞，不得执行任何操作；旧数据缺少身份字段时需保守隔离，不推断归属。
- 已接收但不支持的消息不能永远占据队首导致其他配对饥饿；需定义隔离/终态和监控，不可简单丢弃。
- 平台是否保证重连后重放、适配器离线消息的行为仍待实证；不能宣称全链路至少一次。

## 验收门槛

覆盖同账号不同对话相同消息编号、桥账号变更、非法/零 ID、群聊/转发、同键异内容、崩溃后重复投递、租约过期和撤权竞态。真实 PostgreSQL 并发与真实平台账号各自独立验证。身份规范、迁移和各适配器共同完成之前，保持消息能力和外呼禁用。
