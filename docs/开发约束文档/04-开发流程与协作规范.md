# 04 开发流程与协作规范

> 版本 1.0 · 2026-11-20 · 面向多个模型/开发者轮流推进

## 1. 推进顺序与依赖

```text
M0 环境与骨架 ─┬─► M1 G0 真机验证（关键路径）─┐
               ├─► M2 Core + 短信 + Admin ─────┼─► M3 浏览器外拨 ─┬─► M5 规模与上线
               ├─► M4a QQ 预研 ──► M4a QQ 集成 ─┤                 │
               └─► M4b TG 预研 ──► M4b TG 集成 ─┴─────────────────┘
```

- **关键路径：** M0 → M1（G0 上行音频）。G0 未通过前，语音任务只能做到“可编译 + 单元测试 + 设备模拟器联调”，不得宣称可用。
- M2 不依赖 M1，可完整交付短信与设备管理。
- M4a/M4b 预研（spike）在 M0 后即可启动，不依赖手机。

## 2. 单个任务的标准流程

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 领取 | 14 中状态改为 `DOING（执行者，日期）` | 14 更新 |
| 2 阅读 | 读任务“参考”列的章节与相关模块已有代码 | — |
| 3 设计 | 标注“需设计”的任务，先在日志写 ≤ 10 行实现计划 | 日志 |
| 4 实现 | 按 03 结构与 05/06 契约编写，同步写测试 | 代码 |
| 5 检查 | 运行模块检查命令（12 第 2 节） | 命令输出 |
| 6 验收 | 逐条核对验收标准，收集证据 | 证据 |
| 7 记录 | git 提交；14 改 `DONE` / `REVIEW`；更新 15；写日志 | 提交、日志 |

需要真机或真实账号而当前无法验证的，标 `REVIEW` 并登记到 15 “待真机验证”。

## 3. 模型交接协议

每次会话结束前写交接记录到 `日志/YYYY-MM-DD-序号.md`（模板见 16），必须包含：

1. 完成的任务编号与提交号；
2. 进行中任务的进度、未完成部分、下一步具体操作；
3. 做出的假设与待确认事项；
4. 已知问题、失败尝试及原因；
5. 环境变化（安装了什么、改了什么）。

接手者先读最近 3 份日志与 15 看板。

## 4. 变更管理

| 情况 | 处理 |
|---|---|
| 发现需求错误或遗漏 | 写变更申请（16 模板），标 `BLOCKED`，等用户决定 |
| 修改协议字段 | 变更申请 → 同意 → 同一提交内修改 packages/protocol、fixtures、Kotlin、Python 与 05 文档 |
| 修改已发布表结构 | 只能新增迁移文件，不改旧迁移 |
| 新增 TODO | 直接追加到 14，编号顺延，日志说明来源 |
| 拆分 TODO | 原编号加 `-a`、`-b`，原项标“已拆分” |

## 5. 门槛（Gate）执行

门槛 G0～G4 定义见需求文档 [08](../08-测试与验收计划.md)。

1. 前置任务全部 `DONE` 或 `REVIEW`。
2. 按 16 模板写门槛测试计划：号码、次数、预计话费、人员。
3. 交用户确认，安排测试员。
4. 执行，逐用例记录证据。
5. 结论（通过 / 不通过 / 部分通过）写入 15。
6. 不通过按需求文档 08 处理并通知用户。

## 6. 需求追溯

- 每个 TODO 标注覆盖的需求编号（FR-、C-、NFR-）。
- 测试用例名包含 TC 编号：`it('TC-SMS-05 结果未知不重发', …)`。
- 15 维护 P0 需求覆盖率。

## 7. AI 模型会话节奏

- 一次会话聚焦 1～3 个相关任务，不跨模块大面积改动。
- 开工先跑现有测试确认基线通过。
- 同一错误尝试 3 次仍失败：停止，记录失败尝试，换思路或标 BLOCKED。
- 不为让测试通过而改测试预期，除非预期与文档不符（日志说明）。
- 修改前先读文件，不凭记忆改代码。
