# Isolated v1 SMS event comparison

The standalone `compareParsedSmsReceived` utility accepts two objects shaped as the output of `parseDeviceMessage(value, 'event')` plus a `deviceId`. It returns `equal`, `different`, or `invalid`; both objects must be valid before they can compare equal. It is not connected to ingestion. The comparator input is a constructed envelope: the protocol parser retains `v`, but the current `DeviceEvents` input type omits it and the comparator additionally requires `deviceId`. The caller must have trustworthy v1 provenance; any future integration needs an explicit, reviewed adaptation, not an invented version. An `invalid` result must never be treated as an equal duplicate or used to grant a positive ACK.

The comparison covers the event ID, device ID, version, type, event timestamp, and all seven known `sms.received` payload fields. Keys may be reordered. Unknown, absent, wrongly typed, or accessor fields are invalid; throwing proxy traps also yield `invalid`. Transparent, unstable, or deceptive JavaScript proxies cannot be reliably identified, so only ordinary stable protocol-parsed data objects are supported; arbitrary proxies have no equality guarantee. The device ID must match the protocol-style `dev_` ULID format; this may reject legacy database IDs that do not conform and must not be interpreted as proof that those IDs are absent. The protocol parser strips unknown fields, so this utility cannot detect unknown fields that were already discarded before it received the parsed object. It is not a comparator for arbitrary JSON or a way to recover original wire bytes or original numeric spellings.

Strings compare by JavaScript UTF-16 code units, including U+0000, supplementary pairs and unpaired surrogates; no UTF-8 conversion or Unicode normalization occurs. All numbers must be safe integers with the protocol's sign and timestamp constraints. Negative zero compares equal to positive zero, matching numeric equality for this domain. The protocol's integer schema can accept unsafe values that this comparator rejects. Safe integer acceptance here does not guarantee that every downstream PostgreSQL column, including the PostgreSQL `integer` parts column (maximum 2,147,483,647), can store the value.

For values representable in PostgreSQL JSONB, the field-level comparison is intended to match JSONB numeric and object semantics after JavaScript parsing; U+0000 and unpaired surrogates cannot be stored as ordinary PostgreSQL JSONB strings. This code has not been tested against PostgreSQL and does not establish database behavior, durable custody, duplicate acknowledgement, migration safety, or PDU fidelity. Any production integration requires a separate storage design, validation and integration tests.
